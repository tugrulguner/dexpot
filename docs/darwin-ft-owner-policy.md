# Darwin free-threaded owner scheduling correction

The completed-response CPU-budget handoff bounds how long a connection owner can run Python before yielding, but it did not change the macOS default timeshare scheduling policy inherited by newly created threads. A parent-owned mixed-handler trace showed high wall-clock tail latency despite low handler CPU time; a separate controlled owned-child-thread falsifier showed a repeatable difference when only the worker thread's `THREAD_EXTENDED_POLICY` was changed. These remain local diagnostic experiments, not a framework performance claim or promotion gate.

Dexpot selects its existing Darwin policy adapter once during runtime binding, after application loading, only for Darwin free-threaded serving. Each actual connection owner reads its own policy, switches ordinary policy `1` to fixed timeshare policy `0` when possible, runs the existing ownership loop (including its bounded CPU-budget handoff), and restores its previous setting in `finally` before thread exit. Already-fixed (`0`), unavailable (`-1`), and failed initial changes fall back without changing policy. A failed restoration raises explicitly. This affects neither the acceptor/main thread nor unrelated threads, and does not change QoS, host power settings, handler code, or client workloads.

The existing active-connection/drain accounting and permit reclamation-after-join behavior are unchanged. Existing failures for nested fixed work and prior mixed fixed-policy cases remain valid evidence; this correction narrows the lifetime and owner boundary rather than claiming those failures are resolved. Runtime diagnostics expose only whether the startup adapter was selected; policy reads remain on the owner thread, not a shared request counter.
