# Same-process I/O ownership diagnostic

This is not qualification and does not compare the original stock artifact. It uses one installed current artifact and one serving PID for four original 15-second mixed windows, with four native-client threads and sixteen connections. The diagnostic selects classic raw-worker / shared-owner / shared-owner / classic raw-worker for **future connections only**, at quiescent boundaries. The shared owner remains allocated but idle in classic mode, so that mode deliberately retains its constant footprint and restores the original worker-I/O coupling as a counterfactual—not a candidate fix.

The original application and validator files are copied byte-for-byte. A separately fingerprinted startup sidecar adds three diagnostic-only control routes before route compilation. Mode changes reject overlapping active connections or queued work. Fresh control connections then attest actual membership in the shared owner's socket-state map; this proves backend selection rather than trusting a label. The collector checks serving PID, runtime identity, mode and connection ownership before and after every window; it retains the original native command, metrics, resource ceilings and cleanup requirements. No OS/GIL policy is changed.

The reusable CLI is `run.py --python PYTHON --wheel WHEEL --harness HARNESS_DIRECTORY --wrk WRK --collector COLLECTOR_DIRECTORY --output NEW_DIRECTORY`. It refuses an existing output directory. Only bounded setup/control retries are allowed; native timed windows are never retried. Failed/unknown samples remain invalid. After the final classic window, the saved I/O owner is closed explicitly at shutdown.

`run.py --control-only` exercises real backend transitions, fresh-connection ownership attestations, runtime identity and clean teardown without launching any native timed window. `prepare.py` exercises pinned-source builds, installed identities and runtime guards without native timing. The hosted workflow targets macos-26, the same runner class—not the same physical machine—as prior hosted failures. Local same-PID stability does not establish the cause of earlier cross-process or hosted variation. Additional control routes and runtime pointer selection make this an instrumented diagnostic; no result clears retained acceptance failures.
